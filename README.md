# TRACE-X — Offline Bitcoin Transaction Forensic Intelligence Platform

An offline, Linux-based forensic intelligence prototype built for the hackathon
problem statement **"AI-Powered Monitoring & Analysis of Bitcoin Transaction
Traffic"** (NTRO, Blockchain & Cybersecurity track).

It ingests synthetic Bitcoin network + blockchain metadata (the TRACE-X dataset),
correlates IPs / transactions / wallets, detects anomalies with a real unsupervised
ML model, clusters similar behavior, builds an explainable investigative priority
score, and presents everything in an interactive Streamlit dashboard — with an
IP → Transaction → Wallet entity graph you can explore.

> **Note: this dataset is entirely synthetic.** No output of this system should ever
> be interpreted as identifying a real person, real wallet, or real criminal
> activity. Every score is a **model-generated investigative signal**, not proof
> of anything.

## 1. Architecture

```
JSON / CSV / XML (data/raw/)
        │
        ▼
 [1] Ingestion & normalization  (src/ingestion/loader.py)
        │  → normalizes nested address/amount arrays into one schema
        ▼
 [2] Cleaning & validation      (src/preprocessing/clean.py)
        │  → drops invalid IPs/timestamps, dedups by txid, reports data quality
        ▼
 [3] Offline GeoIP/ASN enrich   (src/geoip/lookup.py)
        │  → uses local .mmdb if present, else falls back to dataset fields
        ▼
 [4] Correlation                (src/correlation/correlate.py)
        │  → derives IP↔TX↔Wallet↔ASN↔Country relationships as typed edges
        ▼
 [5] Entity graph (NetworkX)    (src/graph/build_graph.py)
        │  → IP / Wallet / Transaction / ASN / Country nodes + typed edges
        ▼
 [6] Feature engineering        (src/features/engineer.py)
        │  → per-transaction behavioral features + per-IP graph-topology features
        ▼
 [7] ML: Isolation Forest       (src/models/anomaly.py)      — unsupervised
 [8] Clustering: DBSCAN         (src/models/clustering.py)   — unsupervised
        │
        ▼
 [9] Risk / priority scoring    (src/scoring/risk_score.py)
        │  → transparent weighted 0-100 score, HIGH/MEDIUM/LOW
        ▼
[10] Explainability             (src/explainability/explain.py)
        │  → real, feature-grounded reasons per alert (z-score based; SHAP optional)
        ▼
[11] Evaluation                 (src/models/evaluate.py)
        │  → precision/recall/F1/ROC-AUC/PR-AUC vs synthetic_label (eval only!)
        ▼
[12] Investigation cases        (src/forensics/cases.py)
        │  → links related suspicious transactions (graph + IP + cluster/time),
        │    NOT a simple restatement of a DBSCAN cluster
        ▼
[13] Evidence + Merkle tree     (src/forensics/evidence.py, src/forensics/merkle.py)
        │  → canonical per-transaction evidence records, SHA-256 leaves, Merkle root
        ▼
[14] Local blockchain ledger    (src/forensics/blockchain.py, src/forensics/anchoring.py)
        │  → append-only, hash-linked blocks anchor each case's Merkle root
        ▼
   outputs/  (cached parquet/CSV, graph pickle, JSON reports, forensics/ ledger + evidence)
        │
        ▼
 Streamlit dashboard            (dashboard/app.py)
```

**Key design principles:**
- `synthetic_label` is used **only** in step 11 (evaluation). The Isolation Forest
  in step 7 is trained purely unsupervised on the engineered feature matrix — it
  never sees the label.
- Steps 12–14 (the forensic layer) **reuse** the alerts table and entity graph
  built in steps 1–11 — no ML score, cluster label, or graph metric is
  recomputed. The forensic layer only organizes and cryptographically fingerprints
  outputs that already exist.

## 4. Exact commands to run

From `~/bitcoin-monitor` inside your WSL2 Ubuntu venv:

```bash
# 0. (one-time) make sure your dataset is in place
ls data/raw/trace_x_bitcoin_12000.json

# 1. Install dependencies (if not already)
pip install -r requirements.txt

# 2. Run the full pipeline — ingestion through alert generation
python run.py

# 3. Launch the dashboard (reads cached outputs, does not retrain)
streamlit run dashboard/app.py

# 4. (optional) run the test suite
pytest -v
```

The dashboard will open at `http://localhost:8501`. Because WSL2 forwards
localhost to Windows automatically, you can open that URL directly in your
Windows browser.

To point the pipeline at a **different** raw file (e.g. a `.csv` or `.xml`
export), edit `paths.raw_data` in `config.yaml` — no code changes needed.

### Regenerating a synthetic dataset for testing (optional)

If you ever want a fresh synthetic dataset (e.g. to test with fewer/more
records), you can use:

```bash
python scripts/generate_synthetic_dataset.py --n 12000 --out data/raw/trace_x_bitcoin_12000.json
```

This is only a testing convenience — your real `trace_x_bitcoin_12000.json` is
never modified by the pipeline.

### Demonstrating tamper-evidence (forensic blockchain layer)

```bash
# List anchored investigation cases
python scripts/tamper_demo.py --list

# Deliberately corrupt one field of one evidence record for a case
python scripts/tamper_demo.py --case CASE-XXXXXXXXXXXX --field risk_score --value 0

# In the dashboard's "Forensic Blockchain" tab, select that case and click
# "Verify Evidence" -- it will now report FAILED, naming the exact mismatched txid.

# To restore: explicitly discard that case's stored evidence, then re-derive it
# from the (unmodified) alerts table on the next pipeline run.
python scripts/reset_case_evidence.py --case CASE-XXXXXXXXXXXX
python run.py
# Verify again -- it will report VERIFIED.
```

Re-running `python run.py` WITHOUT the explicit reset step does **not** repair
tampered evidence — this is deliberate (see section 16 below).

## 7. ML method

- **Anomaly detection:** `sklearn.ensemble.IsolationForest`, trained on a
  **standardized** (`StandardScaler`) feature matrix. Fully unsupervised —
  `synthetic_label` is never passed to `.fit()`. Output is converted from
  sklearn's raw `decision_function` (higher = more normal) into an inverted,
  min-max-scaled **0–100 anomaly score** (higher = more anomalous). This is
  explicitly **not** a calibrated probability.
- **Clustering:** `sklearn.cluster.DBSCAN` over the same standardized feature
  space. `-1` labels (DBSCAN "noise") are preserved and shown as-is in the
  dashboard rather than forced into a cluster.
- Both are configurable in `config.yaml` under `model.isolation_forest` and
  `model.dbscan` (contamination prior, eps, min_samples, etc.) without touching
  code.

## 8. Graph method

- `networkx.MultiDiGraph` with typed nodes (`IP`, `Wallet`, `Transaction`, `ASN`,
  `Country`) and typed edges (`OBSERVED`, `INPUT`, `OUTPUT`, `BELONGS_TO`,
  `LOCATED_IN`).
- The dashboard's **Graph Explorer** never renders the full graph (which can have
  tens of thousands of nodes) — it computes a bounded k-hop neighborhood around
  whichever entity you select (`get_neighborhood()`) and renders only that with
  PyVis, keeping investigation paths like `IP → TX → Wallet → TX → Wallet`
  interactively explorable without freezing the browser.
- Graph-topology features (degree, in/out-degree, PageRank, approximate
  betweenness centrality) are computed once during the pipeline run and attached
  to every transaction via its source IP.

## 9. Scoring

`src/scoring/risk_score.py` combines four **min-max normalized (0–100)**
components into one weighted, transparent score:

| Component | What it captures |
|---|---|
| `ml_anomaly` (default weight 0.40) | Isolation Forest anomaly score |
| `behavioral` (0.25) | fan-out, fan-in, transaction burst count, amount variance |
| `graph` (0.20) | node degree, PageRank, betweenness centrality |
| `network_geo` (0.15) | countries touched, wallet/transaction ratio |

Weights are configurable in `config.yaml` and automatically re-normalized if
they don't sum to 1. Thresholds (`high: 70`, `medium: 40` by default) map the
final score to `HIGH` / `MEDIUM` / `LOW`. The dashboard and this README both
state explicitly: **this is an investigative priority signal, not proof of
criminal activity.**

## 10. Explainability

Every alert's `reasons` field is built from **real numbers actually present in
that row** — never invented text:

1. Whether Isolation Forest flagged it, and its exact anomaly score.
2. Its DBSCAN cluster membership (or "noise point").
3. Up to `top_n_reasons` (default 5) additional feature-level reasons, chosen by
   ranking every feature's z-score against the dataset mean/std and only citing
   ones that clear `z_score_reason_threshold` (default 1.5 std devs) — e.g. "high
   fan-out (14 output addresses)", "activity spans multiple countries (4
   countries)".

SHAP (`try_shap_global_importance`) is wired in as a fully optional,
exception-guarded extra — if `shap` isn't installed or errors on your feature
matrix, the pipeline silently continues using the z-score explanations above.

By default, the pipeline uses the dataset's own `geo_country` / `asn` fields —
no setup needed. If you want independent offline verification:

1. Download `GeoLite2-Country.mmdb` and/or `GeoLite2-ASN.mmdb` from MaxMind

2. Place them in `data/geoip/`.
3. `pip install geoip2` (optional dependency, not in the default requirements).
4. Re-run `python run.py` — it will detect the `.mmdb` files and cross-check /
   fill `geo_country` and `asn` using them; if the files or the package aren't
   present, it silently falls back to the dataset's own fields (this fallback
   path is what was used in all local testing).

**No online IP lookup API is ever called**, at setup time or at runtime.

## 12. Evaluation

All of Precision, Recall, F1, ROC-AUC, PR-AUC, and the confusion matrix in the
**ML/Evaluation** dashboard tab are computed **at runtime, from the current
run**, by comparing `is_anomaly_prediction` / `anomaly_score_0_100` against
`synthetic_label` (`src/models/evaluate.py`). Nothing is hard-coded. If your
real dataset's class balance or feature distributions differ from the synthetic
test data used above, expect different (likely better, since TRACE-X's real
anomaly types are quite structured) numbers.

## 13. Investigation cases — organizing detection into forensic units

`src/forensics/cases.py` groups related suspicious transactions into
**investigation cases**, reusing the alerts table and entity graph rather than
recomputing anything. A case is deliberately **not** the same thing as a DBSCAN
cluster. Seed transactions (priority HIGH/MEDIUM, or ML-flagged) are linked into
one case only when at least one of these holds between them:

| Link type | Signal | Reuses |
|---|---|---|
| `shared_wallet` | Two transactions touch the same input/output wallet | Existing Transaction→Wallet graph edges |
| `shared_ip` | Two transactions share a source IP | Existing `src_ip` column |
| `cluster_temporal` | Same non-noise DBSCAN cluster **and** within `temporal_window_hours` of each other | Existing `cluster_label` + timestamp |

Cluster membership alone never creates a link — it must be corroborated by
temporal proximity. Two transactions in the same cluster but months apart, with
no shared wallet or IP, end up as two separate (often single-transaction) cases,
not one. This is directly unit-tested (`tests/test_forensics_integration.py::
test_same_cluster_far_apart_in_time_is_not_one_case`). Connected components over
this linkage graph become cases; case IDs are deterministic (a SHA-256 digest of
the sorted linked txids), so re-running the pipeline against unchanged data
reproduces the exact same case ID and evidence.

The dashboard's **Forensic Blockchain** tab follows the flow: **Case →
transactions → entities → evidence**.

## 14. Merkle-tree evidence — cryptographic fingerprint per case

For every case, `src/forensics/evidence.py` builds one canonical evidence
record per linked transaction (txid, IPs, wallets, timestamp, cluster, scores,
priority, reasons — all values already produced upstream, never recomputed).
`src/forensics/canonical.py` serializes each record deterministically (sorted
keys, fixed separators, floats rounded to 6 decimals) before SHA-256 hashing it,
so the same content always hashes identically and any single-field change
produces a different hash.

`src/forensics/merkle.py` builds a standard binary Merkle tree over a case's
ordered evidence hashes (leaves), producing one **Merkle root** for the whole
case. It also implements:
- `generate_merkle_proof(leaf_hashes, index)` — the sibling-hash path from one
  leaf up to the root.
- `verify_merkle_proof(leaf_hash, proof, root)` — recomputes the root from a
  leaf + proof and compares it to the expected root.

Changing even one field of one evidence record changes that leaf's hash, which
changes the recomputed root, which no longer matches the root frozen in the
blockchain (below) — this is what "verification fails" means throughout this
system.

## 15. Local blockchain ledger — tamper-evident provenance

`src/forensics/blockchain.py` implements a lightweight, fully **private and
local** blockchain — no Bitcoin, Ethereum, other network, or cloud API is
involved anywhere. Each block anchors one case:

```
{ index, timestamp, case_id, merkle_root, leaf_hashes, evidence_count,
  previous_hash, hash }
```

Only hashes and small metadata are stored in a block — **never** raw
transaction data, wallet addresses, or IPs; the full evidence content lives
only in the separate local evidence store (`outputs/forensics/evidence_store.json`).
The ledger is:
- **Persistent** — a single JSON file (`outputs/forensics/blockchain_ledger.json`)
  that survives restarts; a genesis block is created once and never recreated.
- **Append-only** — `src/forensics/anchoring.py` only appends a new block when a
  case is new or its Merkle root has genuinely changed; re-running the pipeline
  against unchanged data adds nothing (`n_unchanged` in the pipeline log).
- **Fully validatable** — `Blockchain.validate_chain()` recomputes every block's
  hash, rechecks every `previous_hash` link, and rechecks every block's own
  Merkle root against its stored `leaf_hashes`, catching tampering with the
  ledger file itself, not just with the evidence store.

## 16. Verification and the tamper-evidence guarantee

`src/forensics/verification.py` is strictly **read-only** — it never rewrites
evidence or re-anchors anything. `verify_case()`:

1. Reads the case's evidence **currently on disk** (whatever it says right now).
2. Re-hashes it with the same canonicalization used at anchoring time.
3. Compares those hashes, one by one, against the hashes **frozen** in the
   case's most recent anchored block.
4. Recomputes the Merkle root from the current hashes and compares it to the
   anchored root.
5. Re-validates the whole ledger's internal hash-chain.

If any single field of any evidence record was altered after anchoring, step 2
produces a different hash, step 3's comparison fails for that record, and
step 4's root comparison fails too — reported as `FAILED`, naming exactly which
transaction's evidence no longer matches.

**Critically, this is never silently fixed.** Re-running `python run.py` derives
cases fresh from the (unmodified) alerts table, but `anchor_cases()` only writes
evidence for a case when that case is new to the evidence store — it never
overwrites a case's evidence that's already present, tampered or not. Restoring
tampered evidence requires the explicit, deliberate
`scripts/reset_case_evidence.py` step. This is unit-tested directly
(`test_rerunning_pipeline_does_not_silently_fix_tampered_evidence`).

**Summary of what each layer is for:**

| Layer | Role |
|---|---|
| AI / graph (existing pipeline) | Detection and correlation — finds and scores suspicious activity |
| Cases (`src/forensics/cases.py`) | Investigation organization — groups related suspicious transactions for an analyst |
| Merkle tree (`src/forensics/merkle.py`) | Evidence fingerprint — one cryptographic hash summarizing a case's evidence |
| Blockchain (`src/forensics/blockchain.py`) | Tamper-evident provenance — an append-only history of what was anchored, when |

## 17. Limitations

- **Synthetic data only.** No real-world Bitcoin attribution is claimed or
  possible from this system.
- The Isolation Forest's `contamination` parameter is a **prior belief**, not
  learned — tune it in `config.yaml` if your real anomaly rate differs
  substantially from ~20%.
- Betweenness centrality is computed on a sample (`betweenness_k_sample`, default
  500 nodes) for performance on large graphs; it's an approximation, not exact.
- DBSCAN's `eps`/`min_samples` are dataset-scale-dependent — if you see either
  "everything is one giant cluster" or "everything is noise," adjust `eps` in
  `config.yaml` (this is a normal DBSCAN tuning step, not a bug).
- The dashboard's wallet-lookup dropdown caps at 5,000 entries for UI
  responsiveness (there can be tens of thousands of unique wallets); use the
  Alerts tab's filters or the txid lookup for anything not in that first slice.
- GeoIP enrichment is best-effort and entirely optional; without a real `.mmdb`
  file it's just a pass-through of the dataset's own geo fields.
- The forensic ledger is a **single-node, local trust model** — there is no
  distributed consensus or proof-of-work (deliberately, since this is a private
  offline evidence ledger, not a cryptocurrency). Its guarantee is tamper
  *detection* (you will always know if evidence was altered after anchoring),
  not tamper *prevention* of the underlying JSON files by someone with
  filesystem access — protecting `outputs/forensics/` at the OS/filesystem
  level is outside this system's scope.
- The ledger grows by one block per new/changed case on every run; for very
  long-running deployments with constantly churning cases this is an
  append-only log with no built-in pruning or compaction.
- Case-linkage is heuristic (three specific signal types); it is an
  investigative aid for grouping related alerts, not a proof of any real-world
  relationship between transactions.
